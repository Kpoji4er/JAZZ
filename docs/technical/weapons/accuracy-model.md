# Каноническая модель точности

## Статус

Эта страница фиксирует целевую формулу, до которой дошёл дизайн в профильной вкладке `Пист` таблицы `JAZZ Weapons V2`. Вкладка `ЭЭЭксперименты` не является источником. Текущий runtime в `Code/AccuracyRangeCTH.lua` ещё не полностью соответствует этому контракту: в частности, стабильный коммит использует степень `1.2`, а целевая формула — `1.25`.

Документ задаёт балансовое намерение. До изменения runtime нельзя утверждать, что все показанные здесь стадии уже исполняются игрой.

## 1. Базовая точность бойца

Для обычного огнестрельного оружия вкладка `Пист` задаёт:

```text
raw_skill = (Marksmanship × 4 + Dexterity × 2 + Level × 5) / 6
base_cth  = round(20 + raw_skill^1.25 × 0.25)
```

Для `MachineGun` текущий runtime подставляет `Strength` вместо `Dexterity`. Сохранение этого исключения в целевой модели требует отдельного решения при реализации.

В формуле листа нет отдельного clamp для `base_cth`; общий предел должен применяться в определённой стадии CTH pipeline, а не добавляться молча внутрь этой формулы.

## 2. Нелинейный вклад меткости в прицеливание

Пусть `m = Marksmanship`, а `clamp(x, a, b) = min(max(x, a), b)`. Нормированный коэффициент прицеливания:

```text
aim_skill = min(100, round(
    min(m, 60)             × 20 / 60
  + clamp(m - 60, 0, 20)   × 20 / 20
  + clamp(m - 80, 0, 10)   × 20 / 10
  + clamp(m - 90, 0, 6)    × 20 / 6
  + clamp(m - 96, 0, 4)    × 20 / 4
))

aim_bonus(clicks) = clicks × AimAccuracy × aim_skill / 100
```

Так разница между 90 и 100 Marksmanship важнее, чем равный по размеру интервал в средней части шкалы.

## 3. Приведённые характеристики оружия

Лист масштабирует кучность и эргономику базовой точностью бойца:

```text
effective_grouping = Grouping × base_cth / 100
effective_handling = Handling × base_cth / 100

grouping_coeff = BulletDropRange × 0.05 + effective_grouping / 100
handling_coeff = EffectiveRange1 × 0.10 + effective_handling / 200
```

`BulletDropRange` далее обозначается `BDR`, `WeaponRange` — `R`, дистанция — `d`, текущий клик — `c`.

## 4. Кусочная дистанционная кривая

Графики вкладки используют два порога: `E1 = EffectiveRange1` и `E2 = EffectiveRange2`.

```text
G = effective_grouping
H = effective_handling
A = aim_bonus(c)
P = grouping_coeff
Q = handling_coeff

if d > E2:
    cth = max((G + A) × (1 - ((d - E2) / (R - E2))^P), 0)
else if d > E1:
    cth = G + A
else:
    cth = H + A + (G - H) × (d / E1)^Q
```

Кривая рассчитывается только для `c ≤ MaxAimActions`. На `WeaponRange` дальняя ветвь приходит к нулю. `min_acc = 0` соответствует нижнему пределу в этой ветви.

## 5. Нерешённое противоречие `EffectiveRange`

Текстовое описание в `Пист` говорит:

```text
E1 = BDR + Handling × 0.25
E2 = min(E1 + бонус прицеливания, WeaponRange - 1)
```

Но таблица и графики используют вручную введённые `EffectiveRange1/2`, которые этой записи не соответствуют. Например, для Beretta 92 указаны `BDR = 7`, `Handling = 70`, `E1 = 2`, `E2 = 6`; буквальная формула дала бы `24.5`.

Поэтому множитель `0.25` и способ построения `E1/E2` пока не считаются исполнимым контрактом. Перед переносом в Lua нужно выбрать одно из двух:

1. исправить формулу порогов и пересчитать таблицы;
2. признать `E1/E2` отдельными характеристиками оружия и добавить их в канонический каталог.

Константа `curve_mult = 1.8` присутствует на листе, но в приведённой выше финальной кусочной формуле не используется напрямую. Её нельзя переносить в runtime без определения стадии применения.

## 6. Укрытия: кандидат на мультипликативное снижение

Статус решения — `candidate`, не утверждённая механика.

Предпочтительный вариант для плейтеста:

```text
cth_after_cover = cth_before_cover × (1 - cover_fraction)
```

При укрытии 30% это даёт `90 → 63`, `50 → 35`, `20 → 14`. Аддитивный штраф `-30` дал бы `90 → 60`, `50 → 20`, `20 → 0` и гораздо легче создавал бы нежелательный ноль для слабого стрелка.

Мультипликативный вариант лучше сохраняет относительный порядок выстрелов и смягчает проблему `0/100`, но применять его нужно после построения базовой дистанционной кривой и до финального округления/clamp. Не следует перемножать уже округлённые UI-проценты.

Нужно отдельно решить:

- складываются ли несколько элементов укрытия в одну `cover_fraction` или перемножаются последовательно;
- действует ли тот же коэффициент на части тела и blind fire;
- как `IgnoreCoverReduction` преобразует `cover_fraction`;
- одинаков ли порядок стадий для UI, AI и фактического броска попадания.

## 7. Условия готовности runtime

Реализация считается соответствующей документу, когда:

- базовая степень равна `1.25` и одинаково считается в UI/AI/runtime;
- определён и протестирован источник `E1/E2`;
- каждый клик использует нелинейный `aim_skill`;
- значения на `d = 0`, `E1`, `E2`, `R - 1`, `R` непрерывны либо разрыв осознанно утверждён;
- финальный clamp и округление выполняются ровно один раз в зафиксированной стадии;
- укрытие имеет утверждённый additive или multiplicative статус;
- тестовая матрица покрывает низкий, средний и высокий навык, все тиры и повреждённое оружие.
