## Что проверено

- Каталог: **182 локальных определения** огнестрельного и тяжёлого оружия, **223 компонента**, **1909 вариантов слотов**. Старые классы включены. Это количество записей, не количество готовых иконок и не полный набор допустимых сочетаний.
- M4A1: **16 прозрачных слоёв** из существующей собранной 3D-сцены, 648×330; итоговая иконка 324×165. 48 поддержанных сочетаний деталей и 48 вариантов с 20-зарядным магазином, честно возвращающих обычную иконку.
- **63 offline-проверки**: смена ствола и зависимого дульника, A→B→A на одном экземпляре, снятие/возврат детали, host entity, неизвестные компоненты/слоты, отсутствие изображения, очистка UI при повторном использовании окна, размеры, alpha, отсутствие обрезанных краёв.
- Сравнение default-композиции с полным рендером той же сцены: средняя абсолютная ошибка RGB около **0.54/255 внутри области оружия**. Это не доказательство совпадения с игрой или всех комбинаций. Отличия самозатенения и перекрытий остаются.
- Изображение contact-sheet визуально осмотрено агентом; приёмка владельцем и проверка JA3 ещё не выполнены.
- Browser click QA не выполнен: встроенный браузер отклонил локальный file URL по политике разрешённых URL. HTML собран и включает готовые планы, но интерактивность в браузере не объявлена проверенной.

## Поправка владельца: прямой магазин на 20 патронов

В фактическом ModItem mapping `M4A1 / JAZZ_MagSmall30_20 / Magazine` выбран **WeaponAttA_MagazineCAR15_02**, прямой ванильный магазин. Объект `M4R_M4A1_Magazine20` из старой Blender-сцены неверен для этой сборки и исключён из прототипа. При выборе 20 патронов демонстрируется fallback целиком; ошибочный магазин не подставляется. Для готовой иконки нужна съёмка фактической детали в игре.

Сцена — исторический snapshot, а не зеркало установленного комплекта. Hash исходной сцены и параметры камеры записаны в [registry.json](demo/registry.json). Длинный ствол с прежними мушкой/цевьём — только исследование геометрии; кабинет может требовать другое сочетание. Выборы demo не являются проверкой допустимости игровой модификации.

## Контракт слоёв

Каждый host получает собственный профиль и общую плоскость, охватывающую **все поддержанные сборки**. Слой хранится полноразмерным RGBA без индивидуального crop/fit. Камера ортографическая, со стороны −X; дуло смотрит вправо. В demo ширина кадра 1.2 м, центр (0, −0.16, 0.04) м, три фиксированных area lights. Одинаковая экспозиция и цветовой профиль для всех слоёв; автоматическая подгонка на смене ствола запрещена. Для пистолетов/тяжёлого оружия допустимы отдельные заранее фиксированные масштабы, но внутри семейства они неизменны.

Источник истины — актуальные `weapon.class`, host `Entity`, `components`, победившие `WeaponComponentVisual`, parent entity и spot transform. Generic Visual проигрывает совпадающему ApplyTo; visual slot не обязательно совпадает с component slot. Компонент может дать несколько геометрических деталей (например, оптику и кронштейн). Пустая строка/false снимает деталь, nil означает дефолт. Невидимое улучшение явно имеет пустой bundle, а не отсутствующее описание.

Порядок demo сзади вперёд:

| Слой | Z |
| --- | ---: |
| Приклад | 10 |
| Ствол | 20 |
| Магазин | 30 |
| Рукоятка | 35 |
| Корпус | 40 |
| Мушка | 45 |
| Цевьё | 50 |
| Оптика / ручка / целик | 60 |
| Дульник | 70 |

Для подствольного и бокового оборудования нельзя назначить один общий Z на весь арсенал: дальняя часть крепления идёт за host, ближняя — перед ним. Производственный профиль должен разделить такие детали на front/back passes или использовать проверенные depth/occlusion masks. Если два меша взаимно перекрываются в разных пикселях, одного порядка PNG недостаточно. Нельзя просто наложить прицел поверх готовой иконки: интегральная старая оптика/магазин останется видна. Требуется голый корпус, проверенные маски замены или полный снимок такой сборки.

Наследуемое крепление имеет полный transform: `world(parent) × spot(parent) × local(part)`. Перемещение/вращение parent меняет слой потомка. В demo дульник имеет отдельные normal/short/long варианты, смещения прочитаны из `.ent`; source assembled уже содержит базовое размещение. Универсальный импорт графа всех host/spot пока не реализован. Порядок `SlotDependencies` — порядок построения 3D, **не** порядок 2D-перекрытия.

Для Mosin менять host rule по Barrel и заново выбирать весь набор; PNG MOSIN_1891/M38/Obrez не являются послойным каталогом. Такой переход проверен синтетическим тестом selector, но арт трёх host здесь не сделан.

Контур накладывать после объединения alpha; demo пишет `icon-*.png` именно так. При будущем UI из нескольких XImage нужны два прохода: все расширенные силуэты позади, затем все beauty-слои; отдельный контур поверх каждой детали даёт ложные швы. Самозатенение разных частей требует дополнительных масок/группового рендера; PNG-наложение не воспроизводит динамические тени автоматически.

## Интеграция без конфликта с исправлением моделей

[selector.lua](../../tools/weapon_layer_icons/selector.lua) — чистый модуль, возвращает host, ordered layers и key. [binder.lua](../../tools/weapon_layer_icons/binder.lua) — проверяемый адаптер с инъекцией UI-операций. Никаких новых globals, wraps, обработчиков игры или записей в weapon.

Будущая точка внедрения — **существующий** `JazzWeaponIcon_BindItemImage` в `Code/InventoryUI.lua`: очистить прежнюю подгруппу, проверить весь план/ресурсы, построить скрытую группу XImage с одинаковым fit и bounds, затем показать целиком. При любом пробеле данных удалить группу и выполнить существующий `GetItemUIIcon() or Icon`. Не возвращать таблицу слоёв из GetItemUIIcon: другие потребители ожидают путь. Chips/rollover и штатные клики должны сохраняться; слой не должен перехватывать мышь. Для UIWeaponDisplay, stash, drag ghost, rollover нужен отдельный аудит прямых обращений к Icon.

Bind должен читать итоговые components после setter, а не запоминать только факт замены. Переиспользование окна, пустой context, удаление окна, смена host и reload обязаны очищать старые слои. Ключ включает revision каталога, class, host и упорядоченные layer IDs/paths/Z. Изменённый арт требует новой revision. Готовая группа хранится только у UI-окна, без PNG/save/network state на оружии. Реализация XImage и её runtime/performance-проверка в JA3 остаются будущим этапом. Binder пока проверен на mock UI.

`Code/InventoryUI.lua`, `Code/Weapon_MosinModular.lua`, setter, `items.lua`, `metadata.lua`, существующие WeaponIcons не изменялись этой задачей. Интеграционные границы переданы основной задаче. Соседние пакеты не модифицировались. Массовую генерацию не выполняли.

## Следующий этап: съёмка в игре

Владелец предложил отдельно запустить JA3 и сфотографировать фактическое оружие. Это предпочтительный источник production-изображений и эталон для проверки слоёв. **Игра в этой задаче не запускалась.**

1. После стабилизации моделей зафиксировать версии пакетов и выбранный профиль комплекта. Запускать через Steam; debug/DAP проверить отдельно по профильному playbook.
2. Сначала M4A1: default, реальный прямой 20-зарядный магазин, короткий/длинный ствол, RIS, приклад, оптика, дульник, under/side. Для каждого кадра сохранять class, components, host, фактический граф прикреплённых сущностей, camera/framing/light и размеры.
3. Зафиксировать камеру и свет для семейства; убрать UI из кадра и анимацию/колебания. Сначала проверить способ получения alpha в поддержанном capture API. Не возвращать dormant WeaponIconBake и не переназначать системные пути конвертера. Если достоверная alpha недоступна, отдельно проверить маску/маттинг; сырой скриншот не объявлять прозрачным слоем.
4. Снять несколько **полных эталонных сборок** до изоляции деталей. Если API позволяет, снимать части с общей камерой и depth/occlusion passes, сохраняя исходную сцену и восстанавливая видимость после серии. Тени и интегральную геометрию проверять сравнением с полным эталоном.
5. Утвердить вид M4A1 и только затем расширять по очереди: старые AR/AK, bolt-action/Mosin с разными host, пистолеты, дробовики, тяжёлое оружие. Каждая запись получает source/capture hash, статус geometry/alpha/overlap/slot coverage, и только после проверки включается в registry.
6. Полностью или частично неподдержанные сборки сохраняют штатную иконку. Не выдавать реестр из 182 классов за готовность 182 комплектов арта. Унаследованные vanilla-классы/слоты, не объявленные локально, требуют runtime-инвентаризации.

## Воспроизведение

Python зависимости: Pillow, lupa. Blender 4.5 используется только для демонстрационного источника, будущий capture может заменить его без смены selector/binder.

```powershell
python docs/tools/weapon_layer_icons/audit.py --output docs/design/weapon-layer-icons/arsenal.json
& '<BLENDER>' --background --factory-startup --python docs/tools/weapon_layer_icons/render.py -- --blend '<assembled M4A1.blend>' --assets '<read-only jazz_assets>' --output '<absolute worktree>/docs/design/weapon-layer-icons/demo'
python docs/tools/weapon_layer_icons/build_review.py --demo docs/design/weapon-layer-icons/demo
.agents/skills/specify-jazz-change/scripts/test-change-spec.ps1 -Path docs/specs/active/JAZZ-WEAPON-ICONS-001.md -Phase Done
```

Повторная сборка заменяет только свои outputs. HTML содержит заранее вычисленные **Lua-selector** планы, а JS только рисует выбранные слои; браузер не подменяет тестируемый алгоритм своей копией.
