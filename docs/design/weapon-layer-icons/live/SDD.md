# SDD: единый арсенал, иконки и имена конфигураций

Дата: 28 сентября 2026. Связанные спецификации: `JAZZ-WEAPON-ICONS-001`, `JAZZ-WEAPON-CAPTURE-001`.

**Решение:** использовать реальные сборки из игры как источник визуальной правды. Иконка и название читают один снимок итоговой конфигурации. Имя изменяется только по явному правилу конкретного семейства. Крепления — отдельный следующий этап, их нынешнее положение не считается окончательным.

Статус документа: **утверждён агентом по прямому поручению владельца**. Это self-review, не независимое ревью и не заявление о human acceptance. Утверждается описанное решение и staged-результат; после команды «ставь как есть пока» установлены 1739 exact-match иконки. Интеграция имён отложена из-за конфликта существующей локализации. Live UI после установки ещё не проверен; см. installation-verification.json.

## 1. Источник и границы

Источник — запущенная владельцем JA3Debug, тестовая карта ModEditor, фактически загруженные InventoryItemDefs/WeaponComponents/entities. Каталог содержит 183 класса Firearm/HeavyWeapon, включая служебные и квестовые записи; это не утверждение, что все 183 доступны в обычной продаже. Старый static snapshot содержал 182 класса и не заменяет live-источник.

Каталог сохраняет class, DisplayName/Plural в текущем языке игры, host entity, defaults, CanBeEmpty, Modifiable и варианты компонентов. Отчёт каждого снимка содержит уже применённые components и фактический граф `vis.parts`: spot, entity, parent. Идентификатор компонента без этого графа недостаточен: одна опция может менять несколько деталей или зависеть от другого слота.

Съёмка не меняет инвентарь наёмников, баланс, сохранения, локализацию или активные моды. Все предметы — временные detached-ID clones. Visual и фон удаляются после кадра; камера, свет и render flags восстанавливаются по завершении задания. Игра остаётся запущенной. Ни dormant bake hook, ни converter override не активируются.

## 2. Визуальный контракт

Одна сторона, дуло вправо, Angle=0. Фиксированная перспективная камера Max, FOV 1200, цель `(100,0,40)` относительно визуала; обычная дистанция 1500, крупный M2/миномёт — 2500. Barrett M82, Gewehr98 и M24 пересняты целиком на 2100, чтобы вместить глушители. Не менять масштаб между модулями одной модели. Исходник 1296×660, staged-иконка 324×165, один внешний тёмный контур 2 px. Pistol/long/long-2100/heavy используют общие crop-профили из manifest; для повторных выпусков фиксировать именно этот manifest, не вычислять профиль по случайному поднабору.

Свет: отдельный объект с defaults класса LightmodelPreset, Default LUT, EV +1, белый sun diffuse, intensity 1000, azimuth 90, altitude 400, без time-of-day, fog, bloom и частиц. Это фиксированная студийная конфигурация, а не текущая погода сектора. Перед beauty ждём 20 кадров. Объект не регистрируется и не изменяет исходный preset. Применённый Lua source и SHA256 сохраняются рядом с каждым заданием.

Уточнение self-review: в раннем source/report студия ошибочно называлась «Day clone». Проверка engine `table.copy` показала, что для Preset он пишет diagnostic assert и возвращает `{}`. Поэтому фактически вся финальная серия использовала defaults LightmodelPreset с перечисленными overrides. Инструмент исправлен на явный пустой объект с этим metatable; повтор M4 подтверждён: среднее расхождение RGB на непрозрачном оружии 0.88/255, p99=5/255 ([сравнение](lighting-consistency.json)). Исходные receipts сохранены без переписывания истории. Также исправлена передача уже строковых названий модов в переводчик, вызывавшая диагностический текст; сама игра и файлы модов не менялись.

Alpha штатного Screenshot оказалась непрозрачной. Поэтому исходные данные состоят из трёх PNG: beauty, silhouette на светлом WeaponModCMTPlane и отдельный фон без оружия. Для маски свет временно переключается на тёмный WeaponModification; это намеренное разделение beauty и маски, а не вычитание двух одинаково освещённых цветных кадров. Покрытие определяется относительной разницей силуэта и фона, noise floor 6%, полное покрытие 85%. Чёрные детали сохраняются, отверстия остаются прозрачными. RGB берётся только из beauty, с удалением чёрного смешения на краю. Исходники сохраняются для смены обработки.

Первый проход `arsenal` и ранние `*-pilot` — диагностические, **не выбирать их как итоговые иконки**. В ранней серии после первого кадра применялся тёмный свет кабинета; этот дефект выявлен на контактных листах. Финальная серия — `production-capture`, результат — `staged` и его manifest. Проверка включает светлый/тёмный фон, alpha, границы кадра и целостность ссылок.

## 3. Охват вариантов

Снимается штатная сборка каждого класса и каждая одиночная замена доступного компонента; пустой слот также снимается, если разрешён и отличается от default. Это покрытие вариантов относительно defaults, **не полный декартов продукт сочетаний** и не доказательство доступности каждого сочетания через UI. В отчёте сохраняются запрошенный и реально применённый компонент; отклонённая замена имеет отдельный статус. У Auto5_quest, Galil_FlagHill, GoldenGun и LionRoar ComponentSlots класса/экземпляра сохраняют старые IDs, а InventoryItemDefs содержит JAZZ-варианты. Обе формы сняты, разница не замаскирована заменой ID в каталоге. Дополнительный quest-capture закрывает именно доступные IDs экземпляров.

Сборки с несколькими одновременными модификациями требуют отдельного набора перед production-приёмкой. Особенно важны Scope/Side/Handguard, подствольники и mount dependencies. Для полной layered-системы нужны зарегистрированные слои и dependency graph; готовые плоские снимки нельзя объявлять независимыми PNG-слоями или автоматически вычитать из них детали.

## 4. Схема представления и fallback

1. Снять атомарно `{class, host, components}` экземпляра. Nil означает наследование default; явное empty остаётся пустым.
2. Применить проверенные правила structural-name. Не менять class/DisplayName/предмет/сохранение.
3. Разрешить visual plan по фактическому host и dependency graph. При неизвестном host, компоненте или несогласованной комбинации использовать существующую целую Icon.
4. Собрать зарегистрированные слои в общем anchor; контур строить по объединённой alpha, иначе каждый стык обводится отдельно.
5. При замене/удалении компонента очистить прежние UI-слои и пересчитать имя и изображение. Не оставлять кэш старого приклада/пустого слота.

`selector.lua`, `binder.lua`, `names.lua` остаются изолированными прототипами. Финальные live-иконки — staging и материал для регистрации. Включение в inventory/HUD требует отдельной реализации в существующих точках UI; второй wrap setter не добавлять.

## 5. Правила имени

Матрица `staged/name-matrix.json`, таблица `staged/names.md` и `weapon-names.csv` охватывают все 183 класса. Тексты из игры и предложенные решения различаются. Список кандидатов не превращается автоматически в правила.

| Семейство | Решение |
| --- | --- |
| AK74 | Обычный приклад → АК-74; штатное складное семейство в обоих положениях → АКС-74. Live-снимки подтверждают различный силуэт. Возврат восстанавливает АК-74. |
| AKM | Штатный деревянный приклад → АКМ; металлический приклад, складывающийся под ствольную коробку, в обоих положениях → АКМС. Live: AKMFoldStock / AKMUnfoldStock. |
| VZ58 | Штатный деревянный → vz. 58 P, штатный металлический складной в обоих положениях → vz. 58 V. Современный тактический приклад возвращает исходное общее имя. |
| AK74M, AK103 | Сохранять собственное имя; складывание штатного приклада не меняет семейство. |
| DragunovSVD | **СВДС отклонено для текущего StockLight.** Видна цельная thumbhole-ложа, не отдельная пистолетная рукоятка со складным рамочным прикладом. Rule остаётся disabled. |

| M4A1 | Реальная 20-ка — прямой `WeaponAttA_MagazineCAR15_02`. Магазин, RIS, положение приклада и просто короткий/длинный ствол сами по себе не дают нового обозначения. |

Условия правил должны включать class, host и необходимые слоты; generic `StockLight` не является исторической идентификацией. При конфликте двух правил сохранять базовое имя и отмечать конфликт. Положение одного складного приклада и выбор другой конструкции — разные вещи.

Сопоставление АКМС — вывод по live-снимку приклада, складывающегося под ствольную коробку, и [руководству Century Arms, стр. 6](https://www.centuryarms.com/media/wysiwyg/pdf/AKMS_Manual_FINAL.pdf), где показана соответствующая конструкция. Для VZ58 [страница Армии Чехии](https://doarmady.mo.gov.cz/o-armade/armypedia/vyzbroj/sa-vz-58) различает P/V; live-снимки JAZZ_VZ58_StockWood, StockWire и StockWireFolded подтверждают соответствующие конструкции. Это сопоставление модели агентом, а не утверждение о заводском происхождении игрового mesh. Источники используются для обозначений, не для изменения игровой механики.

До включения проверить tooltip, cabinet, inventory/HUD, магазин, сравнение, сообщения и plural. Некоторые точки читают DisplayName напрямую; одного GetDisplayName недостаточно. RU/EN production-тексты требуют зарегистрированных T IDs по localization skill; здесь CSV является экспортом аудита, не игровой локализацией.

## 6. Крепления отдельно

Нынешние mounts provisional. Сохранять mount entity/spot/parent отдельно от семантики оружия. Mount revision входит в будущий ключ кеша картинки, но не в правило имени. Новое крепление инвалидирует только затронутые visual recipes; механика наименования остаётся прежней.

После переработки креплений повторить затронутые Scope/Side/Handguard и наиболее нагруженные комбинации тем же сохранённым camera/light/crop-профилем. До этого не «лечить» посадку картинки сдвигом отдельных PNG: это скроет проблему игровой модели. Слои крепления добавлять после проверки геометрии и occlusion; сейчас сохранить целые честные фотографии сборок.

## 7. Порядок production-интеграции

- Выбрать проверенные классы и зафиксировать revision их entities/components/mounts.
- Зарегистрировать реальные слои и defaults; для остальных оставить существующую Icon.
- Встроить resolver/binder в имеющиеся UI-точки с безопасной очисткой и fallback.
- Добавить утверждённые названия и RU/EN локализацию, сохранив уникальные имена и систему Mosin.
- Проверить обратимость замены, clone/preview, load/reload, пустые слоты и обновление открытого UI в игре.
- Отдельно принять самые длинные/короткие/нагруженные сборки. Публикация и установка в активный комплект — отдельное действие.

## 8. Самопроверка и решение

Ревью выполняет тот же агент по просьбе владельца «сам прочитай и апрувни». Проверены границы staging/runtime, честность live-источника, невозможность общего переименования по StockLight, сохранение уникальных имён, отдельная судьба креплений, fallback и воспроизводимость. Ошибочный кандидат СВДС и тёмный первый capture-проход явно отклонены.

Решение: **APPROVE для этого SDD и staged-поставки**, без утверждения о готовой runtime-интеграции. Фактические итоги серии, перечень замечаний и проверка cleanup находятся в `REPORT.md`, `staged/verification.json` и `production-capture/capture-report.json`. Спецификация остаётся в active со статусом implemented после evidence; independent review/human acceptance не выдумываются.

Все активные изображения перестроены из неизменённых полноразмерных RGBA: формат берётся из исходного Icon (324×165 или 162×110), crop индивидуален по alpha>16, отступ 8/5 px, контур 1 px. Это заменяет общий profile crop из раздела 2; масштаб между вариантами теперь определяется заполнением UI, а не общей камерой. Установлены 1739 уникальных снимков. Цвет: насыщенность 1.12, gamma 1.25, gain .86, contrast 1.18 вокруг .40, мягкий нижний предел .65 исходного RGB. Канон рецепта — docs/tools/weapon_layer_icons/icon_layout.py. Original raw/rgba и старый ZIP остаются архивом съёмки; актуальные icons, галерея и contact sheets обновлены.

Автоматическая проверка: совпадение установленных файлов, размеры, прозрачные края, заполнение одной из осей не менее 85%, selector/fallback. Сравнение с оригиналом: size-tone-comparison.png. Во время проверки игра закрылась: окончательное изображение в live UI не подтверждено.


## Цвет v3: привязка к прежним игровым иконкам

По следующему замечанию владельца общая цветокоррекция v2 заменена профилями `color-profiles.json`: 166 локальных оригиналов, по одному фиксированному профилю на класс. Профиль строится по квантилям 5/15/30/50/70/85/95/99 яркости непрозрачной внутренней части default capture и исходной иконки, с монотонной интерполяцией и коррекцией насыщенности. Все варианты класса используют тот же профиль. 14 классов без локального оригинала используют медианный профиль; их список явно сохранён в JSON, служебный подствольник по-прежнему не устанавливается. Геометрия, размеры и alpha v2 не меняются. Evidence: `color-verification.json`, `size-tone-comparison.png`.


Уточнение v3: по запросу владельца усилена обводка до 2 px, RGB 5/6/7, вместо 1 px RGB 22/25/29. Сам силуэт не масштабируется повторно; сохранены размеры и padding v2. Alpha расширяется на дополнительный пиксель контура, что проверяется отдельно.


DesertEagle / HiPower: по замечанию владельца квантильная цветокоррекция заменена гладкой степенной кривой. Прежняя кривая усиливала отдельные диапазоны яркости в 6–13 раз и подчёркивала пятна исходных бликов. Ограничено усиление до 2; исправлены все 18 вариантов, размер и alpha сохранены. `calibrate_color.py` воспроизводит исключение; профили остальных классов и общий fallback не меняются. Сравнение: `docs/design/weapon-layer-icons/live/silver-pistols-comparison.png`; проверки: `pistol-tone-verification.json`. Потёртости, присутствующие в исходной модели/снимке, не ретушировались.


## Native combinations v4 — 29 сентября 2026

Иконка строится в существующем UI binder из нативных фотографий корпуса и деталей. Реестр содержит 1929 nodes для 178 активных классов; крепления имеют собственные идентичности и parent dependencies. Скрытая геометрия и несовместимые компоненты не дорисовываются. Вырожденный host G36 остаётся невидимым структурным узлом. Одинаковая камера внутри семейства, общий crop, прежние размеры ячеек и двухпиксельный внешний контур обеспечивают согласованную сборку. Каждый цветной слой рисуется после всех силуэтов обводки.

Все 9797 эффективных игровых графов сравниваются с Lua selector; перебор сочетаний отделяет запрещённые BlockSlots. При неизвестных данных используется полная прежняя иконка. Сохранения и игровые параметры предметов не меняются. Оба weapon callback UIWeaponDisplay сохранены официальным редактором и перезагружены. Посторонняя перегенерация отделена с сохранением baseline и post-save архивов; load order не меняется.

По дополнительному запросу владельца цветовой проход v4 использует текущие default captures и оригинальные Icon. Гладкие ограниченные кривые заменяют резкие локальные изменения контраста; семейство и все его модули используют один профиль. Размеры, alpha и исходные фотографии сохраняются. Не ретушируются детали оружия и не заменяется реальная геометрия синтетическими изображениями.

Саморевью агентом: архитектура и границы APPROVE. Runtime-композиция проверена в XImage и XInventoryItem; итоговый тон проверен по сравнению с оригиналами и скриншотам открытого инвентаря. 1928 PNG сохранили alpha побайтно; visual/runtime delta APPROVE по саморевью агента. Независимое ревью и human acceptance не заявлены. Имена M1/M1A1/M2/M3 и остальные структурные переименования остаются отдельным незавершённым пунктом.
