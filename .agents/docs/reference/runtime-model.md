# Runtime model и порядок загрузки

## 1) Базовый порядок загрузки

- Сначала игровая Lua, потом зависимости мода, затем код текущего мода.
- Внутри пакета порядок определяется массивом `metadata.lua.code` (а не алфавитным порядком файлов).
- `ReloadLua` **не** делает чистый cold start: глобалы/handlers/threads из старого состояния могут остаться. Из DAP `evaluate` вызывать только через `CreateRealTimeThread(ReloadLua)`, не из потока адаптера (см. `.agents/docs/playbooks/dap-runtime-debug.md`).

## 2) Точки синхронизации с жизненным циклом

- Для class/данных, которые уже собираются модом, ориентироваться на `ClassesBuilt`, `DataLoaded`, `ModsReloaded`.
- Для раннего кода (`items.lua`) не рассчитывать на готовность всех ModItem.

## 3) Сообщения и потоки

- `Msg`/`OnMsg` выполняются синхронно в порядке регистрации.
- `OnMsg` не должен блокировать и тем более спать.
- Не использовать `MsgClear` на engine-уровне.
- Custom message должны иметь префикс `JAZZ_`.
- `GameVar`/`MapVar` не присваивать `nil`; учитывать сохранения и reset-семантику.
- Game-time threads хранят upvalues/байткод в save-снимке: старые версии функций могут вызываться после обновления.

## 4) Объектная модель и UI

- Данные, которые должны жить долго, не хранить только во временной Lua-таблице `CObject`.
- У `SubContext()` нельзя вызывать mutating на временном объекте — изменения в `self` могут уйти мимо целевого объекта.
- `XWindow:CreateThread` обязателен для window threads; закрытие окна убирает дочерние `real-time` потоки.

## 5) Карты и производительность

- `MapCount` и enum/flag методы быстрее и стабильнее, чем полный ручной обход, если нужен только count/фильтр.
- Ограничивай `area/class/flags`; Z-фильтр выносить отдельно, если есть зависимость от высоты.
- Для карты: избегай рекурсивного глубокого анализа всего `Maps/` без явного запроса на целевую зону.
